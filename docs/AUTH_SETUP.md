# BUYORNOT 인증 연결

2026-11-05: 로컬 사이트를 서울 리전 Supabase 프로젝트에 연결했습니다. 공개 키는 Git에서 제외된 `.env.local`에만 저장했습니다. 이메일 가입/확인과 localhost 콜백 2개를 활성화하고 서버 비밀번호 정책을 영문·숫자 포함 10자로 설정했습니다. 실제 가입·메일 인증·로그인 성공 흐름은 아직 검증 전입니다. 카카오 개발자 로그인과 일반 회원용 SMTP 연결이 남아 있습니다.

이메일 회원가입(인증 메일), 로그인, 비밀번호 재설정, 비밀번호 변경, 카카오 OAuth, 계정 확인, 로그아웃을 Supabase Auth로 구현했습니다. 인증 정보와 비밀번호는 Supabase가 관리합니다. 로컬 메모리에 계정을 보관하지 않습니다. 프로젝트를 연결하기 전에는 가입/로그인 입력을 비활성화합니다.

## 1. Supabase 프로젝트

1. https://supabase.com/dashboard 에서 본인 계정으로 새 프로젝트를 만듭니다. 요금제와 지역은 본인이 선택합니다.
2. Project Settings > API에서 Project URL과 **publishable key**를 확인합니다. service_role/secret key는 사용하지 않습니다.
3. 저장소 루트의 `.env.local`에 아래 항목을 직접 입력합니다. 키를 채팅이나 Git에 올리지 마세요.

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

4. Authentication > URL Configuration에서 Site URL을 `http://localhost:3000`으로 설정하고, Redirect URLs에 아래 주소를 **둘 다** 추가합니다.

```text
http://localhost:3000/auth/callback
http://localhost:3000/auth/callback?flow=recovery
```

로컬 접속은 `127.0.0.1`과 섞지 말고 `localhost`로 통일합니다. 인증 링크는 요청한 브라우저에서 여세요(PKCE 검증). 배포 시 실제 HTTPS 도메인을 SITE_URL과 허용 목록에 추가해야 합니다.

5. Authentication > Sign In / Providers에서 Email 가입과 Confirm email을 켭니다. 비밀번호 최소 길이는 10자, 영문/숫자를 포함하도록 설정합니다. 메일 템플릿은 기본 `ConfirmationURL` 링크를 유지합니다. 별도의 DB SQL 적용은 인증에 필요하지 않습니다.
6. 외부 사용자에게 인증 메일을 보내려면 Authentication의 **Custom SMTP**를 연결하고 발신 도메인/주소를 인증합니다. Supabase 기본 발신 서비스는 제한적이므로 외부 사용자 대상 회원가입 테스트를 완료했다고 간주하면 안 됩니다. 발송 한도와 비용은 제공업체에서 확인합니다.
7. 실행 중인 터미널에서 Control+C 후 `npm run dev`로 재시작합니다.

## 2. 카카오 개발자 앱

1. https://developers.kakao.com 에서 본인 계정으로 앱을 생성합니다. 앱 이름은 BUYORNOT으로 설정합니다.
2. 앱의 플랫폼/도메인 설정에 `http://localhost:3000`을 등록하고 카카오 로그인을 활성화합니다.
3. Supabase Authentication > Sign In / Providers > Kakao에 표시되는 Callback URL을 복사합니다. 형식은 `https://YOUR_PROJECT.supabase.co/auth/v1/callback`입니다.
4. 이 주소를 **카카오 로그인 Redirect URI**로 등록합니다. 카카오 쪽에는 사이트의 `/auth/callback`이 아닌 Supabase 콜백을 넣습니다.
5. 카카오 앱의 REST API key와 활성화한 Kakao Login Client Secret을 Supabase Kakao provider 설정에 입력하고 활성화합니다. 이 값들은 웹 소스/.env의 NEXT_PUBLIC 항목에 넣지 않습니다.
6. 설정을 완료하고 provider가 활성화된 것을 확인하면 `.env.local`의 `NEXT_PUBLIC_KAKAO_AUTH_ENABLED=true`를 설정하고 서버를 재시작합니다. 그전에는 카카오 버튼이 비활성화됩니다.
7. 필요한 동의 항목만 설정합니다. 이메일 동의 권한이 없는 앱은 이메일을 요구하지 않고 Supabase Kakao의 Allow users without an email 옵션을 켭니다. 닉네임/프로필은 제공되는 범위에서만 사용합니다. 이 경우 계정 화면에는 이메일 대신 카카오 계정으로 표시됩니다.

카카오 콘솔의 메뉴 이름은 바뀔 수 있습니다. [공식 연결 안내](https://supabase.com/docs/guides/auth/social-sign-in/auth-kakao)를 확인하세요.

## 3. 실제 확인 순서

- `/signup`: 새 이메일과 닉네임으로 가입 → 받은 메일 인증 → `/login`에서 로그인 → `/account`에서 본인 계정 확인.
- 로그인 오류/미인증 이메일/이메일 중복 시 계정 존재나 내부 에러가 노출되지 않는지 확인.
- `/forgot-password`: 메일 요청 → 같은 브라우저에서 링크 열기 → 새 비밀번호 설정 → 로그아웃 → 새 비밀번호 로그인. 만료/재사용 링크도 확인.
- 카카오 버튼 → 카카오 동의 → `/account`로 돌아오기. 동의 취소 시 로그인 화면에서 재시도.
- 서버 재시작 후에도 로그인 계정이 유지되고 로그아웃 후 계정 화면에 접근할 수 없는지 확인.
- 위 검증은 **실제 프로젝트/SMTP/카카오 앱 설정 이후** 실시해야 합니다. 자동 테스트의 SDK 모킹은 외부 연동 검증을 대체하지 않습니다.

## 큐레이션 데이터와 구분

계정 인증만 실제 서비스에 연결했습니다. 큐레이션의 게시물/투표/팔로우는 아직 샘플 데이터이며 운영 DB에 저장되지 않습니다. Supabase 인증이 설정되면 데모 역할 전환을 서버에서 차단하고 모든 실제 사용자는 USER 역할로 표시합니다. 클라이언트/회원가입 메타데이터의 역할을 신뢰하지 않습니다. 실제 계정으로 샘플 관리자/크리에이터 권한을 얻을 수 없습니다. 게시물 저장은 별도의 RLS와 운영 DB 연결이 필요하며 현재 해당 참여 동작은 비활성화합니다.

## 카카오 연결 현황 (2026-11-05)

BUYORNOT 카카오 앱(1639082)을 생성하고 로그인을 활성화했습니다. REST API 키의 리다이렉트 URI를 해당 Supabase `/auth/v1/callback`에 등록했습니다. 로그인용 Client Secret은 기존 활성 상태를 유지해 Supabase provider에만 저장했고 저장소나 로컬 환경 파일에는 넣지 않았습니다. Supabase Kakao와 Allow users without an email이 활성화되어 있습니다. 닉네임만 선택 동의로 설정했고 사진/이메일 등은 요청하지 않습니다.

중요: 현재 Supabase 기본 Kakao 제공자는 `scopes`를 기본 이메일·사진·닉네임에 추가합니다. 이메일 권한이 없는 앱에서는 이것만으로 KOE205가 해결되지 않습니다. 코드에서는 `queryParams: { scope: "profile_nickname" }`으로 최종 OAuth scope를 지정합니다. 실제 `/auth/v1/authorize` 302 응답에서 scope가 `profile_nickname` 하나인 것을 확인했습니다. SDK나 Supabase 변경 후에도 이 동작을 다시 확인해야 합니다.

외부 인증 화면까지의 연결 확인과 실제 사용자 로그인 완료는 다릅니다. 첫 카카오 사용자 동의와 토큰 교환 후 `/account` 도착은 본인 계정으로 추가 검증해야 합니다. 일반 회원용 SMTP는 미연결입니다. 탈퇴/연결 해제 웹훅과 운영용 개인정보 안내 등은 공개 서비스 운영 전 별도 구현이 필요합니다.

## 실제 회원 게시글 (2026-11-05)

`supabase/migrations/202611050001_curation_posts.sql`을 연결된 프로젝트에 적용했습니다. 로그인한 사용자는 실제 Supabase 세션의 ID로 게시글을 작성하고 자신의 글을 수정/삭제할 수 있습니다. 수정은 미답변·30일 이내 글만 허용합니다. 게시글은 DB에 보관되어 서버 재시작 후에도 유지됩니다. 게시물의 닉네임은 작성 시점의 공개 표시 이름이며 이메일/카카오 토큰은 저장하지 않습니다. 신체 정보는 작성 폼에서 사용자가 공개를 선택한 필드만 저장합니다.

공개 글 읽기는 허용하되 쓰기는 인증된 작성자 본인만 허용하는 RLS를 적용했습니다. 작성자·생성 시간·상태를 클라이언트가 바꿀 권한은 부여하지 않았습니다. 익명 REST 읽기 200 및 익명 저장 401/42501을 실제 프로젝트에서 확인했습니다. 실제 사용자 브라우저로 게시 후 새로고침하는 검증은 별도입니다. API 단위 테스트는 인증된 ID 사용, 타인 수정/삭제 차단, 동시 수정 충돌, 저장 오류 처리를 검증합니다.

룸에서는 기존 샘플 큐레이션과 실제 회원 게시글을 함께 표시합니다. 실제 회원 글 쓰기 권한과 데모 관리자 역할은 분리되어 있습니다. 추천 판정·찜·팔로우·룸 개설은 아직 별도 운영 DB 연결 전입니다. 현재는 룸당 최신 1,000개 회원 글을 조회합니다. 규모가 커지면 페이지네이션을 추가해야 합니다.

### 실제 브라우저·DB 검증 완료

2026-11-05 실제 카카오 로그인된 계정으로 상품 `4683168`의 사진·판매가를 미리보기하고 `[기능 확인용]` 글을 등록했습니다. 새로고침 후 유지, 본인 수정 저장을 확인했습니다. 첫 수정 검증에서 Postgres의 마이크로초가 JS ISO 변환으로 잘려 충돌로 오판되던 문제를 발견했고 `posts.ts`에서 원래 `updated_at`을 그대로 사용하도록 수정했습니다. 단위 테스트에도 마이크로초 값의 동시 수정 조건을 반영했습니다.

실제 DB에서 authenticated 역할과 서로 다른 auth.uid()를 사용한 트랜잭션으로 본인 등록·수정·삭제 허용, 타인 수정·삭제 미반영, 작성자 위조 등록 거부를 확인했습니다. 전체 트랜잭션을 ROLLBACK하여 이 권한 테스트 데이터는 남지 않습니다. 브라우저 작성 검증용 글 1개는 사용자가 확인할 수 있도록 유지했습니다. 신체 정보는 공개하지 않았습니다. 128개 단위 테스트와 전체 check/build가 통과했습니다.

## 마이페이지 (2026-11-06)

`/account`를 실제 계정 마이페이지로 구성했습니다. 서버에서 검증한 사용자 ID를 `author_id` 필터로 사용해 본인 게시글만 조회합니다. 샘플 데이터는 마이페이지 통계에 포함하지 않습니다. 홈/내 고민 목록/내 정보 관리, 상태별 집계(만료 포함), 상품·브랜드·고민 검색, 직접 글 작성·수정·삭제와 닉네임 변경을 제공합니다. 게시글 변경 후 계정 페이지 캐시를 갱신합니다. 탈퇴·찜·참여 투표 등 연결되지 않은 메뉴는 추가하지 않았습니다.

닉네임 변경은 검증된 세션의 Supabase 사용자 메타데이터만 변경하며, 작성 당시 이름이 저장된 기존 게시글에는 소급 적용하지 않습니다. 모바일에서는 상단 메뉴와 계정 설정의 로그아웃을 사용합니다. 데이터 조회 오류는 0건으로 처리하지 않고 오류 안내와 재시도 버튼을 표시합니다. 현재 본인 글은 최신 1,000개까지 조회합니다.
