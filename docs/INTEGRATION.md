# 커뮤니티·큐레이션 통합

통합 브랜치: `integration/community-curation`. 원격 push·main 병합·배포는 실행하지 않았다.

## 최신 원본

사용자가 전달한 `BUYORNOT.zip`의 2026-11-06 작업본을 적용했다. 이 ZIP은 GitHub의 이전 `feat/part-a-community` 브랜치보다 최신이며, 별도 홈·공통 상단바·PNG 로고·80개 상품 예시·공유·실제 상품 조회·로컬 파일 저장을 포함한다.

홈·공통 상단바·커뮤니티 CSS, 상품 시드 2개 파일, 상품 이미지 컴포넌트, 커뮤니티 작성폼, 로고 파일은 ZIP과 바이트 단위로 동일하다. 기존 프로젝트의 Supabase 설정·인증·큐레이션·마이페이지·가상 룸·로컬 계정 데이터는 보존했다. 패키지 버전은 같아 추가 의존성이 필요하지 않았다.

## 화면과 연결

| 주소             | 화면                       |
| ---------------- | -------------------------- |
| `/`              | ZIP 원본의 별도 홈         |
| `/community`     | ZIP 원본의 살말 커뮤니티   |
| `/creators/seoa` | 기존 큐레이션 룸과 추천 숍 |
| `/account`       | 공통 마이페이지            |
| `/login`         | 기존 공통 로그인           |

원본 홈의 큐레이션 준비 중 버튼은 실제 룸으로 연결한다. 원본 로고를 큐레이션·마이페이지·기존 로그인 화면에도 사용한다. 원본 상단바의 로그인된 계정 버튼은 My Page로 연결한다. 커뮤니티·마이페이지의 원글 링크는 `/community?post=...`를 사용한다.

커뮤니티는 기존 로컬 테스트 계정과 Supabase의 검증된 ID를 인식한다. ZIP의 개발용 1111 미리보기 로그인은 개발 환경에서만 유지한다. 기존 로컬 테스트 아이디도 원본 로그인 모달에서 사용할 수 있다. 가입 및 소셜 로그인 모달의 미연결 기능은 원본 상태이며, 기존 `/login`·`/signup`·카카오 로그인 경로는 유지된다.

## 데이터 보존

ZIP 원본의 `FileCommunityPersistence`에 따라 개발 환경에서 `.data/community.json`에 글·투표를 저장한다. 기존 임시 상품 6개가 저장돼 있으면 해당 구형 예시만 80개 원본 시드로 갱신하고 직접 작성한 글·투표는 보존한다. 세션은 파일에 저장하지 않는다.

큐레이션 테스트 활동·가상 룸은 기존 `.local-test-accounts/activity.json`을 유지한다. 환경 변수·비밀번호 해시·저장한 비공개 신체 정보·커뮤니티 실행 데이터는 Git에서 제외한다.

## 운영 범위

커뮤니티는 로컬 단일 서버의 파일 저장 방식이며 운영 DB·다중 서버·실시간 집계는 미연결이다. 원본 샘플 상품 가격은 조회 시점의 스냅샷이다. 커뮤니티 상품 조회기는 ZIP의 원본 DNS/IP 고정·리디렉션 검증·응답 제한 구현을 유지한다. 큐레이션 작성폼의 상황·신체 정보 UI와 커뮤니티 작성폼 공통화는 별도 작업이다.

## 검증

`npm run check`: 린트·타입·포맷·270개 테스트 통과. `npm run build` 통과. 홈과 `/community` HTTP 200 확인. 로컬 저장 데이터의 상품 80개 및 구형 플레이스홀더 0개 확인. 원본 제품·스타일·로고 파일 일치 확인. 실제 사용자 신체 정보 입력이나 게시·배포는 실행하지 않았다.

## 2026-11-17 선택 통합

팀원 `feat/community-next`의 `da1a1fa`를 기준으로 홈·살말 커뮤니티·로그인 폼과 아이디 가입 기능을 선택 반영했다. 전체 브랜치를 병합하지 않고 해당 기능 파일을 비교하여 적용했다.

- 홈은 팀원의 최신 버튼 디자인을 쓰되 큐레이션 진입은 `/creators` 목록으로 유지한다.
- 상단바·통합 검색·공통 푸터는 현재 큐레이션 작업본을 유지한다. 로그인 폼도 공통 상단바를 사용한다. 홈과 커뮤니티의 옛 푸터 및 준비 중 SNS는 복원하지 않는다.
- 큐레이션은 팀원의 `CategoryFilter` 디자인만 연결한다. 기존 카테고리 분류와 상품·프로필·관리·추천 숍·전체 상태 탭·하트 효과를 유지한다. 마이페이지는 교체하지 않는다.
- 커뮤니티는 최신순·조회수순·투표순, 상세 조회수 기록, 상품 사진 위 브랜드명 대비 처리와 공통 로그인 이동을 반영한다. 작성 글과 투표 저장 파일은 교체하지 않는다.
- 로그인은 팀원 폼·아이디 중복 확인·아이디로 로그인하는 서버 코드를 반영한다. 명시적으로 삭제했던 `1111` 미리보기 로그인은 복원하지 않는다. 지정 로컬 계정 로그인과 Supabase 이메일·카카오 연결은 유지한다.
- 새 Supabase 아이디 가입/로그인에는 `supabase/migrations/202611140002_unique_usernames.sql` 적용과 서버 전용 `SUPABASE_SERVICE_ROLE_KEY`가 필요하다. 통합 시점 읽기 전용 점검에서 `username_available`은 HTTP 404였고 해당 서버 키는 미설정이었다. 외부 DB 마이그레이션을 실행한 것으로 보고하지 않는다.

변경 전 교체 대상 소스는 `/private/tmp/buyornot-before-team-integration`에 보관했다. 비밀값과 실제 활동 데이터는 복사·출력·업로드하지 않았다. 원격 push·배포·main 병합은 수행하지 않았다.

## 상품 정보 새벽 갱신

앱과 작업 스크립트를 지속 저장소가 있는 같은 호스트에서 실행합니다. 앱 프로세스와 작업 스크립트에 동일한 `PRODUCT_REFRESH_SECRET`을 환경 변수로 주입합니다. 호스트 스케줄러에서 Asia/Seoul 기준 매일 03:00에 다음 명령을 실행하도록 등록합니다.

```sh
node /absolute/path/to/BUYORNOT/scripts/refresh-products.mjs
```

기본 대상은 `http://127.0.0.1:3000`이며 다른 포트면 작업 환경의 `PRODUCT_REFRESH_ORIGIN`을 설정합니다. 앱 단일 인스턴스와 영속적인 `.data/product-refresh` 경로를 사용합니다. 별도 볼륨 경로는 앱의 `PRODUCT_REFRESH_DATA_DIR`로 지정합니다. 스케줄러는 최대 한 번의 명령을 실행하며, 스크립트가 짧은 배치 요청을 반복합니다. 5시간을 넘겨 남은 작업은 다음 실행에서 이어집니다.

공개 커뮤니티 글과 큐레이션 글의 지원 상품 링크를 정규화해 중복을 제거합니다. 최근 14일 이내 등록됐거나 조회수 100회 이상인 상품은 매일 우선 처리하며, 그 외 상품은 3일에 걸쳐 나눠 확인합니다. 쇼핑몰별 동시 요청을 최대 3개로 제한하고 새 요청 시작 간격을 최소 650ms로 유지합니다. 조회 실패 시 마지막으로 확인한 정보를 유지하고 다음 갱신 주기에 재시도합니다. 최초 등록한 상품 JSON은 그대로 보존합니다.
