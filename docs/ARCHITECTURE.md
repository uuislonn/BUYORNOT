# 개발 기반과 경계

## 현재 결정

- 웹 애플리케이션: Next.js App Router + React + TypeScript strict.
- Node.js 24 LTS, npm과 package-lock.json. 설치는 npm ci.
- ESLint, Prettier, Vitest, GitHub Actions로 공통 검증.
- 서버 외부 통합 없이 실행 가능. /api/health는 현재 앱 프로세스의 응답만 확인하며 향후 DB 상태를 보장하지 않음.
- 웹 기본 구성은 기획서 전달 전 임시 선택. 실제 도메인 기능·DB·인증·배포 대상은 미정.

## 폴더

| 경로                | 역할                                      | 협업 규칙              |
| ------------------- | ----------------------------------------- | ---------------------- |
| src/app             | 라우트, 레이아웃, 전역 스타일, API 진입점 | 연결 담당자와 조율     |
| src/features/<name> | 기능별 UI, 타입, 로직                     | 이슈별 담당 소유       |
| src/components      | 공용 UI                                   | 사용처 확인 후 변경    |
| src/lib             | 공용 유틸리티                             | 최소한의 공통 로직     |
| docs                | 요구사항과 개발 지침                      | 기획 변경 시 함께 갱신 |

## 계약부터 합의

여러 기능에 걸친 작업은 데이터 필드, 타입, 오류 형태, 로딩/빈 상태를 이슈에 먼저 명시합니다. 실제 API 준비 전 mock은 담당 기능 내부에 두고 실제 연동과 혼동하지 않게 표시합니다. 공용 파일과 package-lock.json은 동시에 변경하지 않도록 담당자를 정합니다.

## 기획서 수령 후

1. 요구사항과 제외 범위를 문서화합니다.
2. 기능과 계약을 이슈로 나누고 각 담당자를 정합니다.
3. 필요한 DB·인증·API와 비밀 관리 방식을 선택합니다.
4. 기능별 구현, 테스트, PR 리뷰 순서로 진행합니다.

## 도구 호환성

Next.js 기본 린트 플러그인의 peer dependency 범위에 맞춰 ESLint 9.39.5를 고정했습니다. 설치 시 지원 종료 경고가 표시됩니다. ESLint 10은 플러그인 호환 범위가 갱신된 후 함께 올립니다. peer dependency 검증을 강제로 우회하지 않습니다.
